# Review

## Purpose

This doc defines the Review module: the AI-generated weekly review
and the surfaces that present it. It exists because the weekly
review is the highest-value AI output in the app — it is the
moment the app becomes something other than a tracker — and it
needs its own specification.

Review is not a mode. It has no navigation entry. It surfaces when
it is ready (subject to the attention budget) and lives in the
Notes mode as a note.

## Invariants

- The weekly review is generated by Tier 3
  (`04-ai/tier-3-assistant.md`).
- The review is a Note attached to the Day it was generated for.
  If generated late (e.g., the user opened the app Wednesday for
  the prior Sunday's review), the note is attached to the
  *review's scheduled date*, not the open date.
- Review generation is scheduled by default (weekly at the user's
  configured time). It can also be manually requested via the
  command palette. Either way, it surfaces as a nudge through the
  attention budget (`03-experience/attention-budget.md`).
- The review is two paragraphs, not a report. It is a
  conversation, not a dashboard.
- The review cites its data sources and their freshness
  (Invariant 4).

**"Freshness" has to mean fresh at generation, not at reading.**
The block that satisfies this invariant reads "Calendar as of 2
hours ago" — a **relative** claim inside a **static** document. It is
correct once and wrong forever after by exactly the time since
generation: 7 days out after a week, 365 days out after a year. §Review
delivery then says the note "remains in the Notes mode; the user can
read it at any time", so the doc guarantees a stale freshness claim in
the document whose invariant is that it makes one.

Anchoring the clause to **generation** makes it permanently true and
costs one word: "Snapshots taken 20 Sep 18:00 — calendar 2h old, health
8h old." That also separates two facts §Invariants currently conflates
by giving the note one date — **which week this is about** and **when it
was produced** — which the late-generation case needs and the doc does
not provide.
- The review's tone is calm and neutral
  (`01-foundation/identity.md`). No gamification.

## Specification

### When the review fires

- Weekly, at the user's configured review time (default: Sunday
  18:00 local).
- Via the attention budget as a "weekly_review" nudge
  (urgency 4, relevance 6, TTL 7 days, mergeable).
- Deferred if the user is in focus mode or a calendar event, and
  during quiet hours.
- If a protocol review is also due within the same hour, the two
  surfaces are **merged at fire time** into one nudge by the
  attention budget (`03-experience/attention-budget.md`). The
  merged nudge counts as one, not two.

The review can be manually requested via the command palette at
any time: "Weekly review."

### The review content

Two paragraphs, generated by Tier 3:

**Paragraph 1 — What happened.**

- Tasks completed (count, notable ones).
- Habits compliance (aggregate, with any notable patterns).
- Events attended (aggregate).
- Protocol progress (if any active).

**Paragraph 2 — What it suggests.**

- Patterns worth noting ("you hit your meditation habit on 6 of
  7 days you exercised first").
- Slippage worth acknowledging ("3 tasks slipped twice").
- One forward-looking observation ("Tuesday looks dense — 4
  events plus 3 due tasks").

The review does not:

- Prescribe actions.
- Rank the user's week.
- Use gamified language ("great job!").
- Shame slippage ("you failed to...").

### The review card

When ready, the review appears as:

**A nudge.** "Your weekly review is ready." Tap to open.

**A note.** Once opened, the review is a Note attached to the
Day. It lives in the Notes mode and is searchable.

**A calendar card.** The Day view for the review date shows the
review as a preview card.

**What "a Note" means for the surface it opens on.**
`05-modules/notes.md` defines four note surfaces — List, Editor, Note
detail (read-only) and Search — and a Note's Screen *is* the **Editor**:
"A markdown editor. Title field at top, body below. Autosaves on blur and
every 5 seconds while typing. No save button." So reading the app's
highest-value output means opening a markdown editor.

That has a second consequence the invariant above depends on. Invariant 4
requires the review to cite its sources and their freshness, and **both
live in the note body, which is editable**. `05-modules/protocols.md`
states the rule for the other generated note plainly: "The user may edit
a report; the edit is a `note.edited` entry… There is no separate
'original preserved' UI." Two generated notes, one rule — and it means
the citation is enforced by nothing.

The review is also a Note in **Recent**, which `notes.md` defines as
notes edited in the last 14 days, so the user's own list always holds
two weekly AI documents beside their writing. The doc puts it there
deliberately (it should sit beside the writing it is about); the cost is
worth naming rather than discovering.

### Review structure (as a Note)

    ## Weekly review — Sep 14–20

    <Paragraph 1>

    <Paragraph 2>

    ---
    Sources: 14 tasks, 24/28 checks, 6 events, 2 protocols.
    Snapshots taken 20 Sep 18:00 — calendar 2h old, health 8h old.

**Two corrections to the block above, both load-bearing.**

**The window is the seven days ending at the trigger.** The default
trigger is Sunday 18:00, so a review generated on Sunday 20 Sep covers
**Sep 14–20**. This doc previously said "Sep 16–22" in three places —
a Wednesday to a Tuesday, which no Sunday trigger can produce — and
`06-flows/retrieval.md` had copied it. Derive the range from the
trigger rather than writing it out.

**The Sources numbers are the same numbers as paragraph 1.** In this
doc's own example the Sources line read "18 tasks, 4 habits, 7 events,
1 protocol" under a paragraph saying "14 tasks", "24 of 28 habit
checks", "6 events" and "Two protocols were active" — **all four
figures disagreeing with the sentence above them**, in the one part of
the review that exists to be a citation. Compute both from one query so
a disagreement is impossible rather than unlikely.

One consequence of the weekly trigger is worth stating because it is
arbitrary either way: Sunday 18:00 means the window's last day is
incomplete — Sunday's later events and its habit check fall into the
next review.

### The review's tone

The review follows the app's voice
(`01-foundation/identity.md`): calm, legible, instrument-like.
It is a lab notebook, not a coach.

Examples of allowed language:

- "Sleep quality averaged 3.6 this week, up from 3.1."
- "You hit your meditation habit 5 of 7 days."
- "Wednesday slipped — 2 tasks deferred twice."

Examples of disallowed language:

- "Great job this week!"
- "You failed to complete..."
- "You're crushing it!"
- "Let's do better next week!"

### The annual and monthly reviews

Same structure, longer windows:

- **Monthly review.** The calendar month the trigger closes.
  Generated on the first of the month.
- **Annual review.** The calendar year the trigger closes.
  Generated on January 1.

These are optional and off by default. When enabled, they surface
via the attention budget at lower priority than the weekly review.

**One rule governs all three windows: a review covers the period its
trigger closes.** The weekly keeps its seven days; the monthly becomes a
calendar month; the annual is a calendar year. The three then nest
exactly — 52 weeks, 12 months, 1 year — and the annual review can be
computed from the monthly windows the app already produced.

This doc previously said "**4 weeks aggregated**" fired "on the first of
the month". Those are two different definitions of a month: only
**February** is 28 days, so eleven of twelve monthly windows covered
neither the month they were named for. Twelve four-week windows come to
**336 days** against a **365-day** year, leaving **29 days a year**
outside every monthly review — and the annual review's "12 months" was a
third window that matched neither, so the two longer reviews were
independent rather than nested.

**The trade is real and belongs stated.** A four-week window is
**comparable** month to month — "you completed 62 tasks" means the same
thing every time — and a calendar month is **complete**. The doc now
chooses coverage; if comparability matters more, say so and derive the
trigger from the window instead of the other way round.

### Review delivery

The review is delivered once. If the user dismisses it:

- First dismissal: the surface is downranked for 7 days
  (per the attention budget's dismissal decay,
  `03-experience/attention-budget.md`).
- After two dismissals, the surface is suppressed for 30 days.
- The review note remains in the Notes mode; the user can read
  it at any time.

If the user does not open the app on the review day:

- The review is generated on the next app open.
- The note is timestamped for the original review date, not the
  open date.

### The protocol review

Separate from the weekly review, a protocol review fires when a
protocol reaches its review date. It follows the same attention
budget but has a distinct surface:

- Nudge: "Your Sleep protocol is ready for review."
- Opens the protocol detail with the report.
- Surface ID: `protocol_review` (urgency 5, relevance 7, TTL 7
  days, mergeable).

### The combined nudge

When the weekly review and a protocol review coincide (both due
within the same hour), the attention budget merges them into a
single nudge:

    "Weekly review + protocol review ready."

Tapping it opens both:

1. The protocol detail with the report is shown first (urgency
   is higher).
2. A "Weekly review" tab or link opens the weekly review note.

The combined nudge is a **queue behavior**, not a surface. It is
not listed in the attention budget catalog as its own surface ID.
It counts as one nudge against the hourly and daily caps.

If the user dismisses the combined nudge, both surfaces are
dismissed together. They do not re-fire separately in the same
hour.

### The mergeable flag

Weekly review and protocol review are both marked `mergeable: true`
in the attention budget catalog. This is what allows the queue to
merge them. Other surfaces (prep card, contextual nudge, inbox
ritual) are not mergeable and fire independently.

Merging is preferred when:

- Both surfaces are due within the same hour.
- Both are relevant to the current mode.
- The user has not already hit the hourly or daily cap.

Merging does not raise the cap. If the user has already received
three nudges today, neither the merged nor the individual surfaces
fire.

## Examples

**A weekly review.**

    ## Weekly review — Sep 14–20

    You completed 14 tasks, hit 24 of 28 habit checks, and
    attended 6 events. Sleep quality averaged 3.6, up from 3.1
    the week before. Two protocols were active: Sleep (day 18)
    and Focus (day 4).

    Wednesday slipped: 2 tasks deferred twice. Your meditation
    habit correlated with days you walked first (6 of 7). A
    consistent order would make that correlation testable.

    ---
    Sources: 14 tasks, 24/28 checks, 6 events, 2 protocols.
    Snapshots taken 20 Sep 18:00 — calendar 2h old, health 8h old.

**Note what changed in paragraph 2 and why.** It previously ended
"Consider putting the walk before meditation on the calendar" — a
direction to change the user's day, which §The review content forbids in
as many words ("The review does not: Prescribe actions"). The line to
hold is between **changing the user's day** and **describing what the
data suggests**: naming the correlation and its strength is allowed and
is the useful half, and "a consistent order would make that correlation
testable" says the same thing from the describing side.

The original example was doing the thing the doc wanted while the rule
was stated too broadly. The rule is now about directing, not about
observing.

**A standalone weekly review nudge.**

    Sunday evening, 18:00. No protocol review is due.
    Queue fires:
      "Your weekly review is ready."
    User taps. Opens the review note.

**A combined nudge.**

    Sunday evening, 18:00.
    Queue has:
      - weekly_review (urgency 4, relevance 6, mergeable)
      - protocol_review (urgency 5, relevance 7, mergeable)
    Both are due within the hour.
    Queue merges them:
      "Weekly review + protocol review ready."
    Fires once. Counts as one nudge.

    User taps.
    Protocol report opens first (higher urgency).
    A "Weekly review" tab is visible.
    User reads the report, then taps the tab.
    Weekly review opens.

**Dismissing the combined nudge.**

    User swipes the combined nudge away.
    Both surfaces are dismissed together.
    Neither re-fires in the same hour.
    Both notes remain in the Notes mode; the user can read them
    later.

**Dismissing a standalone review.**

    User swipes the weekly review nudge away.
    Nudge suppressed for 7 days.
    The review note remains in the Notes mode.

**A user asking for a review manually.**

    Command palette: "Weekly review."
    Tier 3 generates the review for the current week to date.
    Opens as a note.

**A review generated late.**

    User did not open the app on Sunday.
    User opens the app Wednesday.
    Review generates, timestamped for the previous Sunday.
    Nudge fires on Wednesday (subject to the attention budget).
    Note title: "Weekly review — Sep 14–20."

## What this doc must NOT do

- This doc does not define the retrieval layer. It references it.
  The retrieval layer is `04-ai/retrieval-layer.md`.
- This doc does not define the attention budget. It references
  it. The budget is `03-experience/attention-budget.md`. The
  merging behavior is defined there, not here.
- This doc does not define the protocol report. That is a
  different surface, defined in `05-modules/protocols.md` and
  `04-ai/research-and-protocols.md`.
- This doc does not define the weekly review's prompt. It defines
  what the review is. Prompt structure is in
  `04-ai/constitution.md` and `04-ai/tier-3-assistant.md`.
- This doc does not define tokens, gestures, or motion. It
  references them.
- This doc does not define a Review mode. There isn't one.
- This doc does not list the combined nudge as a surface in the
  attention budget catalog. It is a queue behavior, not a surface.
