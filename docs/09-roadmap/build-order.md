# Build Order

## Purpose

This doc defines the sequence in which to build the app. It exists
because the architecture has dependencies — the log before the
projections, the projections before the modules, the tokens before
the screens — and building out of order produces rework.

The order is not a schedule. It is a dependency graph.

## Invariants

- The event log is built first. Everything depends on it.
- The object model is built second. It defines the atoms and edges
  the log creates and mutates.
- Projections are built third. They are what modules read.
- Design tokens are built before any screen.
- The AI constitution is written before any prompt.
- Modules before flows. Flows reference modules. **One deliberate
  exception, recorded rather than left implicit:** the attention
  budget is built in Phase 1, with the flows, because the shutdown
  and morning-plan flows surface through it (ADR 0013). Deferring the
  caps to a module phase would mean shipping those flows uncapped.
- Infrastructure (sync, auth) is built when the app is local-only
  and usable. It is not built first.

## Specification

### Phase 0 — Foundation (weeks 1–2)

**Goal:** a local-only app that captures, lists, and completes tasks.

1. **Repository setup.** TanStack Start, Tailwind with tokens
   disabled-arbitrary-values, Drizzle, SQLite/WASM, Vitest,
   Playwright.
2. **Design tokens.** `src/ui/tokens.ts` and `tailwind.config.ts`.
   Enforce the linter.
3. **Event log schema.** Drizzle schema for `log_entries`. The
   append-only table.
4. **Event types.** The ~80 event types as a TypeScript
   discriminated union. Payload schemas via Zod.
5. **Log append API.** `append(entry)` writes to SQLite.
6. **Object model types.** Task, Event, Note, Habit, Area, Goal,
   Protocol, Person. The eleven edges.
7. **Projection framework.** `init` and `apply` contracts.
8. **Task projections.** `task_list`, `task_detail`.
9. **Tasks mode.** List, detail, complete, defer, capture (typed
   only; no AI).
10. **Onboarding flow.** Seven screens, with the Tier 1 fallback
    on screen 4 (raw capture; see `06-flows/onboarding.md`).

**Deliverable:** local-only task tracker with a real event log, plus
the onboarding flow that carries a new user to their first completed
task.

### Phase 1 — The Day (weeks 3–4)

**Goal:** the calendar as the hub, with the day as the atomic unit.

1. **Day projection.** `day_view`.
2. **Calendar mode.** Day view, week view, month view, year view.
3. **Daily Note.** Auto-created.
4. **In-app events.** Created and edited.
5. **Shutdown flow.** Three prompts, one preview.
6. **Morning plan flow.** Carryover, today, pick three.
7. **Now line.** Projection and UI.
8. **Design tokens: motion, gesture, haptic vocabularies.** Wired
   in.
9. **Attention budget.** Queue, priorities, caps. Shutdown and the
   morning plan surface through it (ADR 0013).

**Deliverable:** the app now has a shape. Calendar-first, with tasks.

### Phase 2 — Habits and Notes (weeks 5–6)

**Goal:** the remaining two modes.

1. **Habit projection.** `habit_compliance`.
2. **Habits mode.** Today, All, History. Minimum-viable, skip,
   streaks.
3. **Notes mode.** List, editor, Daily Note view.
4. **Note attachment.** Edge 11, all targets.
5. **Capture flow.** Pull-down, sort ritual.
6. **Daily obligations card.** Habit checkboxes and protocol metric
   logging, surfacing once per day.

**Deliverable:** four modes. A real tracker.

### Phase 3 — On-Device AI (weeks 7–8)

**Goal:** Tier 1 and local Tier 2.

1. **Tier 1 parser.** On-device model, confidence thresholds,
   "parsed" chip.
2. **Semantic search.** On-device embeddings.
3. **Command palette.** Commands, direct matches, no assistant
   yet.
4. **Tier 2 local actions.** Break down, find related.
5. **AI constitution.** Written, and the parser carries it.

**Deliverable:** the app feels smart without a network.

### Phase 4 — Protocols and People (weeks 9–10)

**Goal:** the layers.

1. **Protocol entity and projection.** `protocol_report`.
2. **Protocols module.** Proposal, adoption, baseline, active,
   review.
3. **People module.** List, detail, linking.
4. **Areas and Goals.** Filters and parentage.
5. **Review module.** Weekly, monthly, and annual reviews.
6. **Resurfacing.** Forgotten, low-energy, people, streak repair,
   streak milestones.

**Deliverable:** the app becomes a system for self-experimentation.

### Phase 5 — Cloud AI (weeks 11–12)

**Goal:** Tier 3 and research.

1. **Retrieval layer.** Tools and router.
2. **Tier 3 assistant.** Simple queries locally, complex in cloud.
3. **Research pipeline.** Web search, synthesis, notes.
4. **Price-drop alerts.** Re-check a research note's prices and
   surface `price_drop` when they move.
5. **Protocol reports.** Generated.
6. **Weekly review narrative.** Generated by Tier 3 on top of the
   projection.
7. **Test one variable.** Proposed inside the protocol report at the
   review date, as a suggestion in the AI's own output
   (`04-ai/research-and-protocols.md`). It lives here rather than in
   Phase 4 because the report that carries it is Tier 3.
7. **AI audit mode.** Settings view over `ai.proposed`,
   `ai.applied`, and `ai.rejected`.
8. **Cost model.** Metering, quotas, tracking (ADR 0014).

**Deliverable:** the full AI surface.

### Phase 6 — Sync and Auth (weeks 13–14)

**Goal:** multi-device.

1. **Auth.** Supabase, magic-link.
2. **Sync engine.** Push, pull, merge.
3. **Conflict handling.** Order-based resolution.
4. **Initial sync.** Streaming the full log.
5. **Sensitive data defaults.** Local-only for notes, metric
   logs, and person data (see ADR 0008).
6. **Account deletion.** Tombstone flow.
7. **Time machine.** Reconstruct state at a past date. It is the
   recovery path for an unwanted order-based resolution, so it
   ships with sync (`07-infrastructure/sync-engine.md`).

**Deliverable:** multi-device, with auth.

### Phase 7 — Integrations (weeks 15–16)

**Goal:** external feeds.

1. **Calendar sync.** Google, Apple, Outlook.
2. **Contacts.** Platform API.
3. **Health.** Apple Health, Google Fit.
4. **Email forwarding.** Inbound pipeline.
5. **Weather.** Read-only.

**Deliverable:** the app is fed by the user's real life.

### Phase 8 — Shell Apps (weeks 17–18)

**Goal:** iOS and Android apps.

1. **Capacitor setup.** iOS and Android projects.
2. **Native plugins.** On-device STT (push-to-talk capture),
   haptics, secure storage, share sheet, background sync.
3. **Platform polish.** Safe areas, keyboard, back gesture.
4. **App Store submission.** Both stores.

**Why voice waits until here.** Voice capture needs on-device STT,
which arrives with these plugins (`07-infrastructure/stack.md`). A
browser-STT path was considered for Phase 3 and rejected: it would be
a second implementation that the native plugin immediately replaces,
and it would ship voice that behaves differently per shell.

**Deliverable:** mobile apps.

### Phase 9 — Refinement (ongoing)

Everything not in the critical path:

- Draft-day proposals.
- Enhanced search (natural-language filters).

## Examples

**Building out of order.**

    If a developer builds the Tasks mode before the projection
    framework, they will hand-roll state management. When the
    projection framework arrives, the Tasks mode is rewritten.
    The build order prevents this.

**Building in order.**

    Phase 0 delivers a working task tracker. Phase 1 delivers the
    calendar. Phase 2 delivers the remaining modes. By Phase 3,
    the app is already usable, and AI is layered on top.

**A common mistake.**

    Building sync and auth in Phase 0. This creates a false
    dependency: sync makes the app feel complete, but the app has
    nothing to sync. Local-first means local is built first.

## What this doc must NOT do

- This doc does not estimate time. It defines order.
- This doc does not define what each feature does. It references
  the module and flow docs.
- This doc does not define milestones. That is
  `09-roadmap/milestones.md`.
- This doc does not lock in phases as releases. Phases can be
  combined or split as needed.
