Lab 18 · the last mode never drawn

Tasks

This lab should not have been necessary. The status board has carried Tasks mode as done for months, and there is no lab for it — the row has only ever been drawn inside other screens (the Day view's rows, the morning plan's pool, the palette lab's backdrop). A grep for the mode finds it 200 times, almost all of them the dock icon. Work units were counted; coverage never was.

It is also the surface the last decision landed on. ADR 0025 gave the Task a fifth temporal fact, scheduled_time, and put it on the creation surfaces — tasks.md §The task row lists four time facts as chips with a cap of two and a stated priority order. A fifth fact has no chip, no place in that order, and no drawing.

A sixth screen was added after the fact, and from outside the doc set: two reference designs for a task app were shown to this lab, and one of them draws the fields a task doesn't have as icons you tap, which become chips once you have filled them in. That is a claim about the detail screen, so it is measured here rather than argued about. All six screens' rows are now accepted — the row that ships on each is marked Final, and the others are kept as the record of what it cost to get there.

The list

tasks.md fixes one row at row-rich (72px) with metadata and row-default (56px) without it: [checkbox] Title [metadata] over an identity line, and every time fact as a chip on the trailing edge. The cap of two is the one rule in the module that is already a measurement — "one chip leaves the title 195px, two leave it 144px, and three take 232px of the row and leave the title 60px and wrapping."

So this screen re-measures it, at 390px, and then measures it again with the fact that has no chip: a task scheduled at 15:00. The interesting failure is not that the title clips — it is that the row height is fixed, so the pressure shows as title starvation, which looks fine at a glance.

One thing had to be put back before those numbers meant anything. This screen first drew the row without its icon layer — no Area glyph in the metadata line, no glyph inside any chip — and that is a settled decision of design/palette-lab.html (panel D, and the note that V4 supersedes E and F: “the time glyph moved into the chip… chips carry their own glyph”). A real chip is therefore 12px of glyph plus a gap wider than its word alone, and the first pass had measured a chip the app does not draw: it read 210 / 172 / 110 where the palette lab, drawing the real thing, read 195 / 144 / 60. With the glyphs restored this screen measures 194 / 140 / 62 — so the palette lab's figures stand, and the retraction is this lab's and not the doc's.

Two glyphs 03-experience/components.md places in this same line are still drawn as words: user for a linked person and paperclip for the note count. Panel F's density check — “two glyphs in a 13px line… this is where the idea either holds or collapses” — is the reason not to add them without deciding, so that question is open rather than answered. And no fixture here carries an Area without a glyph: all four seeded Areas have one, so the name-only case tasks.md describes — Inbox, and every Area the user creates — is not drawn on this screen at all.

And the row this screen recommends is no longer any kind of table. Three of the five variants below draw the facts as a column — a fixed slot per fact, which is a table with two columns and the title squeezed into the first — and the instruction was to drop the table-like presentations and let the title have its own line. So the recommended row takes the layout the title needs: it owns the first line and wraps when it needs a second, and one context line beneath it carries the section as a word and every other fact as a glyph alone, with no word and no value. The column variants stay below as the record of what they cost, not as options.

Two things were then removed on instruction. The priority dot is gone from every row — and with it the accent border that was the same signal in a second form, because keeping one of the two would have been a substitution rather than a removal. So the list now carries no priority signal at all, where tasks.md's Priority indicator rule (“priority: now shows a small dot in accent-default”) and 03-experience/components.md both describe one. And the sides were put back on the inset the tokens actually specify: every body in this file was padding horizontally by space-7 (24px), which the same table calls *card padding*, where "Screen edge inset is always space-5 (16px) horizontally". With the container gone the row is the list, so the row's own horizontal padding is now 0 and it sits on that inset — which is why the cap figures below moved by 44px rather than the 16 the inset alone accounts for.

The detail

tasks.md spends one sentence on this screen: "Title, notes, subtasks (children), people, scheduled day and time, due, defer, priority, area. Actions: edit, reschedule, link person, link note, break down (Tier 2), research (Tier 2)." Nine fields and six actions, and no layout. The doc also says the four temporal fields are load-bearing — "the app explains it in context" — so this screen is where that promise has to be kept or broken.

And it carries the hole ADR 0025 opened. Every documented control for putting a task on a day is day-granular: the detail's action is "Schedule to day" which "opens date picker", and the defer sheet's rows are Tomorrow · Next week · Someday · Pick a date…. The field now holds an hour, and nothing in the set can set one — Tier 1 parsing is the only control that has ever produced a time of day. So the question this screen answers is not where the fields go. It is what the hour control is.

The detail, filled

The screen above answered where the nine fields go. It answered it for a task that has all nine — and that is the case a detail screen spends least of its life in. A task is captured with a title and nothing else; the fields arrive one at a time, over days. So the common detail is a mostly-empty one, and the question here is the one the screen above never had to ask: what does a detail look like when half the fields are not set?

The form below is the only thing in this lab taken from a reference rather than from a doc: a task card that draws the fields it does not have as icons on the trailing edge, which open a picker and become a chip once filled. Five readings of it, and every other variable is held still — the same task, the same four children expanded in all five — so the single thing that changes is how a missing field is drawn. The task is the one from the screen above, before it was filled in.

One form in it needed a decision rather than a doc. 03-experience/components.md's placement table already allowed a glyph to mark a slot — the protocol card's Goal and Metric do exactly that — but every slot it carried was labelled, and icon-only buttons were allowed only for the unlabelled mode icons, on the strength of a tooltip that a phone does not have. Measurement is what made the question unavoidable: the same four fields cost 168px as glyphs and 335px as words, and the worded form fits the 340px column with 5px to spare. That trade is ADR 0029, and the recommended row below is drawn under it. The children are the second question: they are the only place a sub-task's fraction can be seen at all, and 05-modules/habits.md has already decided how the app says a fraction — "counts, not percent, because counts are honest."

The four scopes

tasks.md §Scopes gives each scope one sentence. Read as predicates they are not a partition, and the doc set already contains the proof of it: three docs say an overdue task appears in the Today scope — resurfacing.md, disruption.md and ADR 0006 — while Today's own definition names neither due nor overdue. It reads “tasks scheduled for today, plus tasks with a defer date of today or earlier.”

The same gap runs the other way. Next is keyed on priority, not on dates — “tasks with priority: now or priority: next that are not scheduled for today” — so a task whose only date is a deadline belongs to no scope at all but All. That is not a corner: it is what Tier 1 produces. “Call dentist Tuesday” parses to due and nothing else (`04-ai/tier-1-parsing.md`), and priority: later — the third of the three values — is claimed by no scope either.

The doc's own Today example, over today's actual definition.

The completion log

Three docs describe this surface and no two of them agree on what it is. 05-modules/tasks.md calls it the completion log and gives it a window — “the filter shows tasks completed in the last 30 days by default.” 06-flows/completion.md calls it the completed log and gives it a different one — “filterable by day, week, month.” And 03-experience/surfaces.md files it as a Screen whose entry is “All → filter 'Completed'”, which is a state of the All scope and not a surface of its own — the same call this set already corrected once, for the Time machine.

And the row cannot say the one thing the log exists for. `tasks.md`'s row carries five time facts as chips — due · scheduled · duration · cadence · deferred — and completed is not among them, so a completed task's completed_at has no chip, no column and no place in the row. completion.md calls this “the ‘what I did’ view… deeply motivating and rarely seen by the user unless they go looking” — which is an admission about discoverability sitting in the doc that owns the surface.

Baseline

All, filtered. The rows are ordinary task rows, because nothing says otherwise.

Changed
Nothing. Two taps to reach — the All scope, then the filter — with a 30-day window and the standard row.
Cost
Five completions look exactly like five open tasks. The row's vocabulary has no `completed` chip, so the one fact that makes this a log — when — is absent, and a record with no times in it is a list of titles. The order is a sort, not a story.
Against rules
Three. `surfaces.md` says Screen and the doc says filter-state; `tasks.md` says 30 days and `completion.md` says day/week/month; and `01-foundation/identity.md` calls this the “what I did” view while `completion.md` admits it is “rarely seen.”
Impeccable

A record is a document: days as headings, times in the row, counts that close each day.

impeccable · operate
Completed 30 days
Changed
The filter becomes a window in the header, and the list becomes a document: a day heading with its count, then that day's completions each carrying its time. “Tuesday · 3” is the sentence the log exists to say.
Cost
Day headings cost a row every few items, and they only pay for themselves inside a window — over 30 days the heading for a day with one completion is four fifths furniture. It also abandons the scope control: this screen no longer shows which scope you are in, because it is not one.
Against rules
One: `surfaces.md` files this as reachable from All, so a screen with no scope control has to say how you get back — the entry it documents stops being true.

The answer to “what did I do” is today. The long tail is what search is for.

Changed
The window goes entirely and the log answers one question, today, with the count in the header. Anything older is a search or a time-machine request, which `06-flows/retrieval.md` already owns.

RecommendedFinal

A state of All, not a screen; a day heading, a time in the row, and one window vocabulary.

Takes
Impeccable for the day heading and the count — a record should say “Tuesday · 3”. Frontend design for the leading time column and the tabular figures. Design taste for the instinct that the frequent question is today — but as the default window, not as the only one.
Fixes
Three things the drawings made unavoidable. The log stays a state of All — the scope control is still on screen, so surfaces.md's entry (“All → filter 'Completed'”) becomes literally true instead of filing a state as a screen. The row carries its own time in a leading column, which is the fact the log exists for and the chip vocabulary cannot hold. And the window is the app's one window selector, so the set stops having three vocabularies for one control.
Still needs
Two things, and the first is not a layout question. One: `completed` needs a chip or a column, and that is a specification decision — the row's five facts are a closed list in `tasks.md` and a completion is a sixth; the log is where they part company. Two: `completion.md` says the log is “rarely seen by the user unless they go looking” and `01-foundation/identity.md` calls it the app's motivating view — so a surface that is supposed to reward the user is reachable only by someone who already knows it is there. Making the app say something about a finished day is a nudge, and a nudge needs a `SurfaceId`, a toggle and a budget line (`03-experience/attention-budget.md`, ADR 0013) — an ADR, not this screen.
