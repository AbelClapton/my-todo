Lab 15 · the two AI surfaces, and the last of the set

Tier 2 & Tier 3

Two docs, side by side, describing the only two places the AI touches the user. Tier 2 is "the highest-value AI in a daily tracker" — a long-press on one thing. Tier 3 is "the escape hatch" — the palette, for queries that span modules.

Both are governed by tight invariants, and three of those invariants are the ones broken here: Tier 2 always produces a proposal, Tier 2 is never ambient, and the cost model owns the numbers. In each case the doc that owns the rule is right and the docs that describe surfaces have moved past it.

Two siblings, two shapes

Tier 2 and Tier 3 both return proposals. They describe the same object twice, with different field names.

one shape · the log already has it
Tier 2 { tier: 2, action: string, proposal: { type: 'text' | 'mutations' | 'note', mutations?: [{ target, operation, payload, explanation }], note?: { body, attached_to, metadata } }, explanation: string }
Tier 3 { type: 'answer' | 'proposals' | 'clarification', proposals?: [{ target, operation, payload, explanation }], summary: string }

The log settles it

ai.proposed is one entry type for all three tiers — { proposal_id, tier: 1 | 2 | 3, context, proposal, explanation }. So whatever the two responses look like on the wire, the log stores one shape, and the explanation field is part of it.

And Tier 3 has no explanation

It has summary at the top and explanation per proposal. Tier 2 has explanation at the top and per mutation. One field, two names, one concept — and the log picks the name.

Changed
Both docs use one name for the top-level line — explanation, matching the log — and Tier 3's type values are renamed so that type means the same thing in both. The response envelopes stay different, because an answer and a card genuinely are.
Cost
Two renames. The invariants, the flows and the log are unchanged, which is the point — the log was already the single shape.
Against rules
A field that the log stores under one name and two docs describe under two is a field an implementer will map twice. `object-model.md`'s rule — the log is the shape, projections follow it — applies to responses too.
Three tiers, three logging rules

Every call, every application, or only the proposing ones — and one of them is a middle case nobody states.

Tier 1 "Every Tier 1 application is logged" applies
Tier 2 "Every Tier 2 call is logged" calls

It logs calls, so a pure read is logged — "View history", "Find related", "Prep me". Tier 3 explicitly does not log a pure read: those go to the diagnostics buffer. Same action kind, opposite rule, one tier apart.
