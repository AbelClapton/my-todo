Lab 07 · the module the app is built around

Protocols

protocols.md calls protocols "the app's defining feature" and "what make the app different". It is also the only module with a lifecycle — five statuses and a time box — and the only one whose central noun is a measurement.

Three things came out of reading it, and two are cross-module. The card is four lines in 96px, by the same arithmetic that broke the note row. "Not scored" is a state no surface can draw. And the proposal sheet offers an action that opens a second sheet — which is the same one-sheet rule that already decided the Event detail and New event. This is its third surface.

The protocol card

protocols.md §The protocol card gives the card's exact contents, and its exact height: row-hero (96px).

Four lines — title, Goal with the day counter, metric with its baseline, habits with compliance. The day counter is the one to watch: with the documented defaults (baseline 14, duration 28) the card reads "day 18 of 42", and 42 appears nowhere else in the doc set. The report writes those same two numbers as 14 baseline + 28 active — so the card's M is a derived sum that no doc names, while the doc gives two different renderings for it: day N of M and baseline: day N of M.

The lifecycle

Five statuses, three scopes, and one action whose threshold two docs state differently. protocols.md §Abandonment: "Generates a report if the active period was ≥ 7 days." research-and-protocols.md §Abandonment: "A report is generated if there is enough data."

The threshold matters because of what the baseline period does: the metric is logged daily throughout it. So a protocol abandoned on day 13 of a 14-day baseline has thirteen days of real measurements, and the rule — which counts only the active period — produces no report at all. The data existed and nothing reads it.

Nothing. Statuses, scopes, and the abandon threshold as written.

Two. §Abandonment's ≥7-day rule contradicts research-and-protocols.md's "enough data"; and the status diagram allows proposed → abandoned while §Scopes files abandoned under Past — a scope whose definition includes protocols that were never adopted.
Impeccable

The threshold counts logged days, not active days.

measure the data, not the phase
Abandon at baseline day 13 of 14 13 days logged
As written active period was 0 days no report
As changed ≥ 7 days with metric entries report generated

The baseline is a measurement, not a warm-up — §Baseline says the metric "surfaces daily in the daily obligations card", so those thirteen days are readings. A rule that counts only active days throws them away.

Changed
The report threshold becomes "≥ 7 days with metric entries", counting baseline and active alike — so the rule reads the data the app actually collected.
Cost
A baseline-only report compares nothing: there is one mean and no second condition, so the report's whole structure (delta, one-variable test) has no referent. Generating it means writing a report shaped for a result into a case with no result.
Against rules
One: research-and-protocols.md §Review and report specifies the report's structure as a comparison. The change makes the threshold honest and the artefact undefined — which is a reason to change the artefact, not the threshold.
Frontend design

The abandonment report is a note — so write the note it can honestly write.

reuse the container · it already holds prose

## Reading protocol — closed during baseline

**Duration:** 13 baseline days, no active phase.

**What the data showed:** pages read averaged 24. No comparison is possible — the experiment did not start.

**One thing worth keeping:** the 13 baseline readings are on record, so a future proposal starts from a measured baseline instead of a guess.

Changed
A baseline-only abandonment still writes a note, and the note says plainly that there is no comparison — because "Reports are Notes" (protocols.md §Invariants), and a note can hold a sentence that a report-shaped template cannot.
Cost
It makes "abandoned" produce an artefact in almost every case, which weakens the signal §Abandonment is protecting: a report should mean something happened. And the "one thing worth keeping" line is invented — no doc asks the app to be encouraging about a stopped experiment.
Against rules
One: research-and-protocols.md says the report "must state explicitly that" certain things, in a fixed structure. This note is a different shape, so it is a second report format rather than the same one applied to less data.
Design taste

"Past" should not contain protocols that never ran. Delete proposed → abandoned.

cut the tell · a commitment you can abandon is not one
proposed the only exit is Adopt, or let it expire Proposed
baseline abandonable — the metric is running Active
active abandonable Active

"Past" then means experiments that ran, which is what a history is for.

But §Invariants says "abandoning is a valid result" and the diagram is explicit about three source statuses. Deleting an arrow contradicts the invariant's spirit, and a proposal the user does not want still needs a way to disappear.

Changed
Removes the proposed → abandoned edge, so Past contains only protocols that produced data. Declining a proposal becomes a dismissal, not an abandonment.
Cost
A proposed protocol can then only leave proposed by being adopted. The doc gives no expiry, no dismiss, and no other exit — so the Proposed scope becomes a list that only grows, which is the state the Scope exists to prevent.
Against rules
One: the status diagram is a specification, and this deletes an edge from it. It also removes the only path by which "abandoning is a valid result" applies to a protocol that has not started — i.e. the least consequential case the invariant names.
Recommended

Keep the edge, name the threshold once, and compute the review date.

fix the two silences, keep the model
Report threshold one number, one owner ≥ 7 logged
Review date adopted + baseline + duration day 42
Day counter M the same sum 42
Past on abandon from proposed: no data, no report allowed

Three fields, one computation. The review date is 42, the card shows "of 42", and the report writes "14 baseline + 28" — the same sum stated three ways, which is exactly why no doc noticed that only two of the three were defined.

Changed
Three fixes, all definitional. (1) The report threshold is stated once, in protocols.md, and research-and-protocols.md points at it — counting logged days so baseline data is not discarded. (2) The review date is defined as adoption_date + baseline_days + duration_days. (3) day N of M's M is the same sum. Past keeps proposed → abandoned but the scope's definition says it holds protocols that ended, whether or not they ran.
Cost
Two docs change for one number, and the review date now becomes a value the app must store or derive consistently — if duration is edited before adoption (which §Adoption's "Edit" allows), the review date moves, and nothing says whether it is recomputed or frozen at adoption.
Still needs
Whether extending a protocol moves the review date. §Review says a user can "extend, which creates a new protocol version" — a new version with a new adoption date and a new review date, or the same window extended? The doc says "new protocol version" and never says whether the old one's data carries over, which decides whether an extension is a continuation or a second experiment.

Changed

Whether the app says this at all is a decision about tone, and the module that owns the app's tone (02-architecture/constitution.md) has a rule about explaining, not about valuing.
