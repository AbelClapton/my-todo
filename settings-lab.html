Lab 10 · the last module

Settings

settings.md exists because settings "were referenced throughout the docs… but were never canonically listed." It is a surface, not a mode, reached from the command palette or a gear icon, and it is the app's longest list by an order of magnitude: 49 rows across 12 groups.

Its own invariants are unusually tight — one typed key per stored value, groups stable, exactly three confirmed actions — and the tightness is what makes the defects visible. Two keys in the log's SettingsKey union have no row here, one action writes 41 log entries with nothing linking them, and the surface opens in two different containers depending on which door you came through.

The list

settings.md §Behavior: "The list uses row-compact (44px) rows, grouped by section with a type-title-3 header and space-8 separation between groups."

Every number needed to size the surface is in that sentence, so this screen uses it. Twelve groups, forty-nine rows, and no search — while the entry point the doc names for the surface is the command palette, which is a search field.

Reset all settings

settings.md §Notes: "Reset all settings. Resets every SettingsKey to its default. Logs one system.settings_changed per key, in one append batch. The UI undo toast reverses the batch atomically by compensating every entry it created; no shared grouping ID is stored in the log. Does not touch user data. No confirmation dialog; undo is the safety net."

The invariant is careful about *why* it needs no confirmation — the action is reversible, and the three confirmed actions are confirmed because they are not. What the sentence does not say is what the reversibility rests on: a toast, and a log that was deliberately built without the one field that would make the batch recoverable.

Baseline

One tap, 41 entries, five seconds of undo.

no lens · the control arm
Reset all settings confirms: no

The batch, as it lands in the log:

41 entries, appended together, with nothing connecting them.

The toast is the only record that these 41 belong together, and it lasts 5 seconds.

After it expires the 41 entries are indistinguishable from 41 deliberate edits.

Changed
Nothing. The action, its batch, and the five-second window, as specified.
Cost
…
Against rules
One, and it is the invariant's own reasoning turned around: §Invariants says destructive actions have a confirmation and there are exactly three, with everything else "undoable instead". This is undoable for five seconds and then not — and the doc states the mechanism that makes it unrecoverable (no grouping ID) in the same paragraph that relies on the undo.
Impeccable

Give the batch an ID. The log already has the shape for it.

one batch, one identifier · make the undo durable

The same batch, with the entries named:

41 × system.settings_changed
each carrying batch_id: 'rst_01H8…'

Recoverable from the log, at any time41 entries
Undo window no longer load-bearingany time

A batch id also lets Rebuild projections distinguish a reset from 41 deliberate edits — which is the operation that would otherwise bake the reset in permanently.

Changed
A batch identifier on the entries a reset creates, so the reversal does not depend on the toast still being on screen.
Cost
It adds a field to `system.settings_changed` for one action's benefit — and the doc's reason for omitting it is not laziness: a batch id in the log is a step toward transactions, and the log is deliberately a list of individual facts. Every future bulk action will want the same field.
Against rules
Two: event-log.md states adding a type needs an ADR (changing a payload's shape is the same kind of change), and this doc explicitly records the omission as a decision — "no shared grouping ID is stored".

Two containers

settings.md §Behavior: "Settings open as a full-screen sheet from the command palette or as a panel pushed from the gear icon."

One surface, two containers, chosen by which door the user came through. That alone would be untidy rather than wrong — app-shell.md explicitly supports a sheet opening a second one and returning. What makes it a defect is where the doc files things: surfaces.md records the Area list as "Screen (in Settings)" — and a Screen is layer 1 ("Screens, lists, the timeline") while a sheet is layer 4 (Transient).

So the same surface puts the same contents in a different layer depending on the door, and the table it is being placed in contradicts its own count.

The key union

settings.md §Invariants: "Every setting that stores a value has a SettingsKey in 02-architecture/event-log.md. Adding a key is a doc change." event-log.md holds the union — 28 entries, two of them templates that expand to twelve surfaces and three channels.

The invariant runs one way: a setting implies a key. It does not say a key implies a row. So the union and the surface can drift, and they have — by exactly one key.

Baseline

Every key in the union, against every row in the surface.

Against rules
One, by omission: the invariant is stated in one direction only, so a key with no row is not a violation — which is why it survived. It is still a value the app can store that the user cannot see, set, or unset.
Impeccable

Make the invariant bidirectional, and checkable.

Rewritten invariant:

"The SettingsKey union and the rows on this surface are the same set. A key with no row is a setting the user cannot reach; a row with no key is a control that stores nothing. Both are errors, and a test asserts the two lists are equal."

Changed
The invariant becomes an equality between two lists, which makes it testable and makes "adding a key is a doc change" mean both docs change.
Cost
Some keys legitimately have no row. integration.calendar.enabled may be written by a connect flow rather than a toggle — a value the app sets on the user's behalf, with no control. Making the sets equal forces a toggle for every such key, which is how a settings screen acquires switches nobody wanted.
Against rules
One: the current invariant is deliberately one-directional, and the doc's phrasing ("every setting that stores a value") suggests the author was thinking about the same asymmetry. The row makes it strict; the honest version distinguishes settable keys from observed ones.

Cost
It puts UI taxonomy into the event log's type union, and the log is meant to describe facts rather than surfaces. A "destructive" key is not a property of the value; it is a property of what the app does with it, and encoding it in the payload couples the log to a screen.
Against rules
One: event-log.md defines the union so "the settings surface and the log stay in sync" — a sync concern, not a classification one. Widening it is a change to the log's purpose, and the doc's own note says adding a key is a doc change rather than a mechanism.
